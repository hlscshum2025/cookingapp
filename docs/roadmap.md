## 版本口径（2026-08-11 确认）

- **第一版：基础设施版，已完成。** 网站、Supabase、账号、RLS、核心菜谱页面、手动录入、正式域名均已可用。
- **第二版：初步应用版，当前进行。** 以“可直接打开 B 站原视频 + 手工整理菜谱”为正式主流程，完成手机端全部功能入口、10 条真实内容闭环、备份恢复和日常使用验收。
- **第三版：批量自动化版，后续再做。** 自动字幕/音频转写、OCR、AI 结构化、批处理、断点续传和更多来源适配统一放到第三版，不阻塞第二版。
- 微信小程序先保留兼容性和封装评估，不要求第二版 Web 上线前完成；先把响应式 Web 主流程稳定下来。

V1 是“可以开始验收和录入”的第一版，不是最终完整版。现在最重要的工作不是继续堆新功能，而是验证数据能稳定保存、手机能随时访问，再开始批量整理内容。

## 阶段 3：第二版核心使用闭环（工程能力已通过，真实内容待验收）

旧开发计划中的 **M3“核心菜谱”已经通过**：菜谱库、详情、编辑器、厨房模式、日志、标签和来源链接都已具备。当前路线图的阶段3还包含真实内容验收，因此不能只用“数据库已有14条记录”直接判定全部完成。

第二版确认采用以下流程：

1. 从收藏夹 JSON 保存 BV 号、标题、UP 主和原链接；
2. 在软件内根据 BV 号打开 B 站原视频，不下载视频到数据库；
3. 用户边看原视频边在手动录入工作台填写食材、步骤、火候和个人调整；
4. 保存后再次打开、编辑，并在实际制作后增加做菜日志。

自动转写、OCR、AI 自动结构化和批量导入不属于第二版完成条件。

从 199 条中选择差异较大的 10 条：快手菜、主食、烘焙、炸物、汤、肉菜、西餐、替代食材明显的菜。

每条完成：

1. 核对来源、UP 主与视频链接；
2. 整理食材、用量、厨具、步骤、时间和火候；
3. 添加中英德食材名与德国购买关键词；
4. 标记未知和待核验内容，不让 AI 猜测；
5. 加入自己的成功版本和调整；
6. 实际制作后写一条日志；
7. 测试搜索、标签、厨房模式和分享页面。

完成标志：10 条菜谱从导入到实际做菜、修改、再次打开全部走通。

当前判断：14条云端记录证明数据库和读取链路可用，但仍需选出其中至少10条，确认每条都有可用食材/步骤、个人版本，并至少补齐一次制作日志后，阶段3才算完整通过。

## 阶段 4：第三版批量整理与自动化

第三版再按每批 20–30 条推进：

- 清理非菜谱、重复和以后不想做的内容；
- 获取字幕或简介，AI 生成候选字段；
- 人工校对食材、用量、步骤、火候和标签；
- 做过且成功的菜标为“已成功/常做”；
- 尚未尝试的内容保留“待尝试”；
- 每完成一批就导出备份并检查数据库记录数。

不要等待 199 条全部整理完才使用；10 条、30 条、100 条都应形成可用版本。

## 长期决策原则

- 个人修改和实际制作记录优先于完整搬运视频
- 可追溯、可编辑和可备份优先于全自动
- 健康与食材安全信息必须显示来源和核验状态
- 正式数据不进入公开 GitHub，密钥永不提交
- 先让响应式 Web 稳定，再决定是否开发小程序
- 每个外部服务都保留替换接口，避免被单一平台锁定
