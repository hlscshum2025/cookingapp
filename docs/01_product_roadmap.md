# 01｜CookingApp 全生命周期产品路线图

更新日期：2026-08-18  
用途：记录所有版本中新增、完成、延期、替代和放弃的功能。当前版本的具体执行只写入 [`02_v2_workboard.md`](./02_v2_workboard.md)。

## 1. 状态定义

| 状态 | 含义 |
|---|---|
| 已完成 | 已进入正式基线，并完成对应验收。 |
| 进行中 | 正在开发、合并、迁移、部署或实机验收。 |
| 已计划 | 已确定版本，但尚未开始。 |
| 候选 | 值得保留，尚未承诺版本。 |
| 已延期 | 明确保留，但因前置条件移到以后。 |
| 已替代 | 目标保留，方案已经换成另一种实现。 |
| 已放弃 | 不再实施，并记录原因。 |

## 4. V2｜初步应用版

### 4.1 厨房词典与地区本地化

- 进行中：食材与厨具的简中、英文、德文基础词典；
- 进行中：德国普通超市 / 亚超优先分类和用户购买经验；
- 已完成第一批骨架：`zh-CN`、`zh-TW`、`en`、`de` 的导航、状态、设置和导入中心标题；
- 已计划：台湾地区词汇层，而不是只做字符级简繁转换；
- 已开发：用户在桌面右上角或设置中选择四种界面语言，保存在现有 `profiles.locale`；用户原始菜谱内容不被改写；
- 已计划：地区词条来源、审核状态、别名与版本；
- 已计划，暂不实施：词典拆分为食材、调料、厨具、特殊厨具四类；分类保留扩展能力；
- 已计划，暂不实施：登录用户提交新词汇或更改申请，包含 locale、地区、别名、来源、理由与证据；
- 已计划，暂不实施：管理员词汇审核区负责通过、拒绝和合并重复提案，审核结果可追溯；用户提案不能直接覆盖正式词典；
- 已计划：德国小票中的商品简称、包装名、商店缩写通过 market alias 映射到稳定 canonical ingredient；
- 已延期：奥地利、瑞士等更细地区词汇，等德国实际使用后扩展。

### 4.2 选菜、采购、库存与成本

- 进行中：菜谱加入采购车、多菜食材聚合、德超/亚超清单和 CSV；
- 已合入 main：采购行可勾选“已购买”，复制与 CSV 自动排除本次已购买食材；
- 已合入 main：账号级“线上冰箱”保存常备食材/调料，采购清单自动排除已有库存；支持“用完了”二次确认后移出库存；
- 已完成数据库结构：`pantry_items` 在 DEV / PROD 均启用 owner-only RLS；业务备份升级并覆盖线上冰箱数据；
- 已计划：份数缩放、同单位合并；
- 已计划：如真实使用需要，再把“本次已购买”从浏览器状态升级为跨设备采购会话；
- 已计划：采购价格、币种、包装净量、商店、每次做菜成本和每人份成本；
- 已计划：调料按次数或固定估价均摊；
- 已计划：小票识别后生成“待确认采购项”，确认后才进入成本与可选库存更新；
- 已延期：实时门店库存和价格抓取，必须保留地区、时间与来源，不能硬编码。

### 4.3 公开菜谱与运营

- 进行中：私人菜谱申请公开、管理员审核、公开快照与只读公开库；
- 已合入 main：成品图片封面与公开点赞；
- 已计划：最新/热门排序、管理员批量审核和运营标签；
- 已计划：公开内容的再次修改必须重新审核。

### 4.4 多来源导入

- 已合入 main：统一 `SourceAdapter` / `SourceDraft` 与通用分享文本入口；
- 进行中：B 站、下厨房、小红书和普通网页真实样本验收；
- 已合入 main：下厨房普通菜谱 URL 自动转换为 MIP 读取，预填标题、作者、用料和步骤；
- 已替代：小红书服务器自动抓取不作为主方案，改为“分享链接识别 + 浏览器人工通过登录/验证 + 页面提取器 + CookingApp JSON”；
- 已合入 main：小红书可弹出独立浏览器小窗口查看原页，并提供 App deeplink；小窗口只负责查看和人工验证，不跨域读取正文；

- 已开发：来源能力用“符号 + 短文字”说明内嵌视频、自动读取、页面提取、手工核验和 OCR 开发中，不只依赖颜色；

### 4.5 德国小票 OCR 与 Document AI 学习线

- 已计划：先用 OpenCV 做灰度、去噪、阈值、轮廓、四角检测和透视矫正，理解“图像预处理 → OCR”的完整流水线；
- 已计划：Web 端通过独立 Python vision service 接 PaddleOCR，Next.js 保持业务/UI 职责；
- 已计划：定义统一 OCR provider contract，为未来 Apple Vision / Google ML Kit 的手机本地识别保留同一输出结构；
- 已计划：OCR 原始商品名先进入地区/商店 alias 层，再映射现有 canonical ingredient，并复用简中、繁中、英文、德文词典；
- 已计划：数据库设计 `shopping_receipts`、`receipt_ocr_runs`、`shopping_receipt_items`、`purchase_records`、`ingredient_market_aliases`，但 migration 必须先在 DEV 验证；
- 已计划：使用 CORD v2 学习 receipt parsing 和做 baseline；公开 CORD 标注无需逐张重做，学习阶段抽样核验；
- 已计划：收集德国不同超市、角度、折痕、光照的小票建立独立测试集；以后如现成模型长期存在系统性错误，再考虑微调/训练；
- 已计划：任何 OCR 候选默认未核验，V2 不允许识别结果静默直接改变库存或成本；
- 已计划：小票原图、支付/交易类无关信息按 owner-only 私有数据处理，公开接口不得返回。

具体执行任务、CORD 操作顺序和代码目录建议见 [`02_v2_workboard.md`](./02_v2_workboard.md)。计划数据库结构同步规则见 [`03_dev_prod_database_sync.md`](./03_dev_prod_database_sync.md)。

## 5. V3｜图像自动化、库存提醒与并行厨房版

### 5.1 来源视觉自动化

- 视频关键帧 OCR；
- 图片中的食材/字幕/用量候选提取；
- 小红书等视频/图片来源的受控辅助导入与人工核验；
- AI 菜谱候选结构化；
- 大批量后台队列、断点续传和失败重试；
- 来源证据与个人修改的差异比较和细粒度回滚；
- V3 优先复用已有字幕和视觉证据，不把“深入学习/自研语音识别模型或目标检测模型”作为本版完成条件。

### 5.2 线上冰箱增强

- 为库存项增加购买日期、开封日期和可选保质期；
- 临期提醒与已过期提醒；
- “用完了 / 丢弃 / 补货”状态与采购清单联动；
- 提醒只作为辅助，不自动判断真实食品安全状态；
- 视真实使用再增加数量、包装单位和多存放位置（冰箱 / 冷冻 / 常温）。

### 5.3 多菜谱并行厨房

- 一次选择多道菜进入“本次做菜”；
- 手机左右滑动切换菜谱；
- 平板双栏或多栏同时显示；
- 每道菜独立保存当前步骤、完成状态和计时器；
- 全部菜总览集中提示下一步、翻面、关火和预计完成时间；
- 步骤绑定锅具、灶位、烤箱等资源；
- 单厨房自动调度，再扩展多人 / 多厨房协同与移动交接。

## 6. V4｜语音识别、YOLO 与多模态 AI 研究版

### 6.1 语音识别（ASR）学习与接入

- 系统学习 ASR 基础：波形/频谱、特征表示、CTC、Attention/Transformer、encoder-decoder、语言模型与解码；
- 先阅读并运行成熟开源模型（以 Whisper 类模型为 baseline），理解音频切分、时间戳、语言识别和解码过程；
- 对 B 站/小红书做饭视频建立 `audio → timestamp transcript` 流程，保留模型、版本、置信度和原始证据；
- 不要求从零训练大型 ASR；只有真实中文做饭语音、口音、背景音乐等错误足够稳定后，再评估 fine-tune / adapter / domain vocabulary；
- 研究推理性能、GPU/CPU 成本与本地/云端部署边界。

### 6.2 YOLO 与厨房目标检测

目标不是为了“必须自己训练 YOLO”，而是用 CookingApp 的真实场景系统学习目标检测、数据标注、训练、评估和部署，并逐步把识别结果接入现有词典、库存和菜谱数据层。

计划场景：

- 冰箱 / 冷冻柜照片中的食材候选：鸡蛋、牛奶、蔬菜、水果、饮料、包装肉类等；
- 厨房台面上的食材、调料瓶、锅具、刀具、砧板、量勺和容器；
- 德国超市货架或商品照片中的商品包装、价格标签和条码区域；
- 做饭视频中的锅、碗、食材包、调料容器和关键操作对象；
- 与 OCR 组合：YOLO / detector 先定位价格标签、包装文字或小票区域，再交给 OCR 读文字；
- 与线上冰箱组合：目标检测只生成“候选库存项”，必须经过 canonical ingredient 映射和用户确认后才能修改库存。

学习与实现顺序：

```text
预训练 YOLO baseline
  ↓
读取图片 / 视频并画 bbox
  ↓
理解 confidence、IoU、NMS、mAP
  ↓
收集自己的厨房 / 冰箱图像
  ↓
人工标注小规模数据集
  ↓
train / val / test 划分
  ↓
fine-tune
  ↓
错误分析
  ↓
导出 ONNX / 移动端或服务端部署评估
```

设计约束：

- 识别到“一个红色包装盒”不等于已经知道它是哪种 canonical 食材；视觉类别和食材词典必须分层。
- 对包装相似、遮挡严重、袋装散装等情况保留 `unknown` / candidate，不伪造确定结果。
- 自己的数据集需要记录图像来源、授权、标注版本和 train/val/test 划分，避免同一视频相邻帧泄漏到训练集和测试集。
- 如果现有预训练模型已经满足某一任务，不以“必须从零训练”作为目标；优先通过 fine-tune 学习完整工程流程。

### 6.3 多模态证据融合

CookingApp 中的“多模态”不是简单把很多数据一起丢给一个黑盒模型，而是把不同来源的证据对齐到同一时间轴/实体后再融合与交叉验证：

```text
音频 ASR：“加一点盐”
字幕：“加入盐”
视频帧 OCR：“盐 5 g”
YOLO / 视觉检测：出现盐罐 / 量勺
         ↓
时间轴对齐 + 实体归一化
         ↓
候选：盐 / 5 g
         ↓
证据一致性与冲突检测
         ↓
结构化菜谱候选 + evidence + confidence
```

- 研究语音、现成字幕、关键帧 OCR、YOLO/视觉对象、来源简介之间的一致性；
- 同一事实必须允许保存多个 evidence，不把 AI 输出覆盖原始证据；
- 当“语音模糊、画面明确”或多个来源冲突时，输出待核验而不是强行选一个答案；
- 可逐步比较规则融合、置信度加权、LLM/多模态模型融合等方案；
- 建立可复现实验集和指标，避免只看单个成功案例。

### 6.4 研究数据与训练边界

- CORD/公开数据用于学习通用 document parsing；德国小票使用独立真实测试集；
- YOLO / 目标检测优先使用公开预训练权重做 baseline，再建立小规模自有厨房/冰箱数据集；
- 视频研究集按“语音、字幕、OCR、视觉检测、最终人工确认菜谱”保存 ground truth；
- 公开数据集的已有标签不需要全部人工重标，但自己的训练/测试 ground truth 必须人工抽查和最终复核；
- 优先 fine-tune 或 adapter，不以“从零训练大模型”为目标；
- 所有训练数据明确版权、个人隐私与是否允许用于训练。

## 9. 路线图维护规则

1. 新需求先写入本文件并标记版本与状态；没有版本的进入候选池。
2. 开始实施时同步到当前版本工作表，写负责人、前置条件和完成定义。
3. 用户反馈先进入 `99`，确认处理后再转成当前版本任务。
4. 发布后更新 CHANGELOG；版本结项后把经验沉淀到对应 `00` 类复盘。
5. 删除、替代和延期不能从历史中抹掉，必须保留原因和日期。
