# 01｜CookingApp 全生命周期产品路线图

更新日期：2026-08-27
用途：记录所有版本中新增、完成、延期、替代和放弃的功能。当前版本的具体执行只写入 [`02_v2_workboard.md`](./02_v2_workboard.md)。

## 1. 状态定义

| 状态 | 含义 |
|---|---|
| 已完成 | 已进入正式基线，并完成对应验收。 |
| 进行中 | 正在开发、合并、迁移、部署或实机验收。 |
| 已计划 | 已确定版本，但尚未开始。 |
| 候选 | 值得保留，尚未承诺版本。 |
| 已延期 | 明确保留，但因前置条件移到以后。 |
| 已替代 | 目标保留，方案已经换成另一种实现。 |
| 已放弃 | 不再实施，并记录原因。 |

### 4.5 小票 OCR、YOLO 与线上冰箱视觉识别

V2 同时建立两条不同的识别线：小票属于“文字与版面理解”，冰箱/台面照片属于“目标检测、分类与实例分割”。YOLO 不能替代 OCR；OCR 也不能判断照片里有几个苹果。

#### 4.5.1 小票 OCR 与 Document AI

- 已计划：先用 OpenCV 做灰度、去噪、阈值、轮廓、四角检测和透视矫正，理解“图像预处理 → OCR”的完整流水线；
- 已计划：Web 端通过独立 Python vision service 接 PaddleOCR，Next.js 保持业务/UI 职责；
- 已计划：定义统一 OCR provider contract，为未来 Apple Vision / Google ML Kit 的手机本地识别保留同一输出结构；
- 已计划：OCR 原始商品名先进入地区/商店 alias 层，再映射现有 canonical ingredient，并复用简中、繁中、英文、德文词典；
- 已迁移 DEV：`shopping_receipts`、`receipt_ocr_runs`、`shopping_receipt_items`、`purchase_records`、`ingredient_market_aliases` 和私有 `receipt-images` 已建立并核验；PROD 仍按 `03` 等待明确发布批次；
- 已计划：使用 CORD v2 学习 receipt parsing 和做 baseline；公开 CORD 标注无需逐张重做，学习阶段抽样核验；
- 已计划：收集德国不同超市、角度、折痕、光照的小票建立独立测试集；以后如现成模型长期存在系统性错误，再考虑微调/训练；
- 已计划：任何 OCR 候选默认未核验，V2 不允许识别结果静默直接改变库存或成本；
- 已计划：小票原图、支付/交易类无关信息按 owner-only 私有数据处理，公开接口不得返回。

#### 4.5.2 冰箱、台面与袋装果蔬识别

- 已计划：先用预训练 YOLO / YOLO-World 做开放词汇 baseline，识别苹果、香蕉、番茄、牛奶、鸡蛋、包装肉类等粗类别；baseline 只用于测可行性，不直接写库存；
- 已计划：对堆叠或袋装果蔬使用实例分割，而不只画矩形框；可用 YOLO segmentation 或 SAM 类模型生成/修正 mask；
- 已计划：使用 [Grocery Store Dataset](https://github.com/marcusklasson/GroceryStoreDataset) 的 81 个细类 / 42 个粗类做迁移学习与分类基线，再建立 CookingApp 自有冰箱、台面、透明袋、反光、遮挡和不同光线数据集；
- 已计划：用 [YOLO-World](https://github.com/AILab-CVC/YOLO-World) 验证开放词汇提示，用 [Segment Anything](https://github.com/facebookresearch/segment-anything) 辅助实例 mask；超市货架/结账场景可参考 [RPC](https://github.com/RPC-Dataset/RPC-Dataset.github.io) 与 [Unitail](https://arxiv.org/abs/2204.00298)，但这些数据不能替代家庭冰箱数据；
- 工程判断：超市称重台通常有固定相机、固定托盘、受控距离，并可融合重量、PLU/条码、包装文字和多帧图像。CookingApp 手机拍照环境更混乱，因此首版必须输出候选类别、数量范围与置信度，让用户确认后才更新线上冰箱；
- 袋装果蔬重点难点：透明袋反光、折射、遮挡、多个实例粘连、品种外观相似和域偏移。不能只下载一个通用 YOLO 权重就宣称完成，必须用真实袋装照片做独立测试；
- 许可边界：Ultralytics 与 YOLO-World 采用强 copyleft / 商业许可组合，数据集也各有许可。V2 研究可以运行 baseline；正式商业发布前必须逐项确认代码、权重和数据许可，不能默认“GitHub 可下载 = 可闭源商用”。

#### 4.5.3 V2 统一安全边界

- 图片识别、OCR、条码和重量信息都先写候选层，并保留 provider、model/version、bbox/mask、置信度和原始证据；
- 同一物体可以由视觉类别、包装 OCR、条码和重量共同确认；证据冲突时保持 `unknown`，不强行映射 canonical ingredient；
- 只有用户确认后的候选才能生成采购记录、成本行或库存变更。

具体执行任务、CORD 操作顺序和代码目录建议见 [`02_v2_workboard.md`](./02_v2_workboard.md)。计划数据库结构同步规则见 [`03_dev_prod_database_sync.md`](./03_dev_prod_database_sync.md)。

V2 不另写一套互不相干的“手机版网站”。业务、账号和数据逻辑保持共用，但手机端采用独立的信息架构与响应式组件，不把桌面页面等比缩小。

- 已计划：逐页完成 mobile-first GUI 重构；手机优先使用底部导航、单列任务流、全屏/抽屉式录入和底部主操作，桌面保留侧边栏、多列与并排核验；
- 已计划：导入中心、手工录入、播放器、采购、设置、公开菜谱按 `360 / 390 / 430 / 768px` 代表宽度测试，禁止输入框、文件框、对话框和浮层越出视口；
- 已计划：触控目标、键盘弹出、横竖屏、刘海安全区、浏览器返回与未保存草稿恢复纳入手机验收；
- 已开发，待 HTTPS 实机验收：将现有 Web App 升级为可安装 PWA。PWA 仍是同一个网站，已加入 Web App Manifest、192/512 与 maskable/Apple 图标、`start_url`、standalone 显示、安装引导、Service Worker 和离线页；
- 安全边界：Service Worker 不盲目缓存 Supabase 私人响应、登录令牌或用户菜谱；首版只缓存静态外壳和明确允许的公共资源，离线编辑必须等冲突/重试策略完成后再开放；

## 5. V3｜超市发现、完整语言、自动化与协作版

### 5.1 来源视觉自动化

- 视频关键帧 OCR；
- 图片中的食材/字幕/用量候选提取；
- 小红书等视频/图片来源的受控辅助导入与人工核验；
- AI 菜谱候选结构化；
- 大批量后台队列、断点续传和失败重试；
- 来源证据与个人修改的差异比较和细粒度回滚；
- V3 优先复用已有字幕和视觉证据，不把“深入学习/自研语音识别模型或目标检测模型”作为本版完成条件。

### 5.2 超市特价发现与菜谱决策（承接 V2 识别能力）

- 用户在超市对特价包装商品、散装食材或短视频拍照/录像，系统先检测商品区域，再结合包装 OCR、条码、视觉类别和词典 alias 生成可编辑候选；
- 候选映射到稳定 canonical ingredient 后，计算“现有库存 + 现场候选食材”能做的菜，并列出仍需购买的配菜、调料和缺口；
- 提供两个结果出口：直接打开 CookingApp 自有菜谱候选，或按标准搜索词跳转到 B站、小红书、下厨房三个来源入口；平台搜索遵守公开接口、登录和跳转边界，不绕过限制；
- 对散装/袋装果蔬只给类别、数量范围与置信度；包装商品优先融合包装文字和条码，不把相似包装的视觉猜测直接当成确定食材；
- 保存“看到了什么、选择了什么菜、最后买了什么”的可选决策记录，为以后推荐排序服务；没有用户确认不得写入库存或采购事实；
- V2 先完成小红书截图、小票 OCR、冰箱/台面识别 baseline 与统一 candidate；V3 负责把这些能力串成超市现场的完整决策工作流。

### 5.3 线上冰箱增强

- 为库存项增加购买日期、开封日期和可选保质期；
- 临期提醒与已过期提醒；
- “用完了 / 丢弃 / 补货”状态与采购清单联动；
- 提醒只作为辅助，不自动判断真实食品安全状态；
- 视真实使用再增加数量、包装单位和多存放位置（冰箱 / 冷冻 / 常温）。

### 5.4 聚餐协作、饮食记账与多菜谱并行厨房

- 聚餐协作：创建聚餐、挂菜、投票/点菜、认领主厨/帮厨/采购、过敏与饮食限制提醒、预算与任务状态；
- AA 分账：采购前预算与购买后小票分离，支持成员不参与某项、个人垫付、退款和结清状态；
- 饮食记账：从已核对小票中只提取食品/外食/饮品等账目，排除押金、购物袋和非食品项目，可按月、商店、食材与菜谱汇总；
- 聚餐小游戏只作为协作活动的可插拔模块，不进入成本核算核心，也不影响账目真实性；
- 成本核算、聚餐协作和饮食记账共享 `purchase_records` / receipt evidence，但分别拥有自己的业务表、权限和界面；

- 一次选择多道菜进入“本次做菜”；
- 手机左右滑动切换菜谱；
- 平板双栏或多栏同时显示；
- 每道菜独立保存当前步骤、完成状态和计时器；
- 全部菜总览集中提示下一步、翻面、关火和预计完成时间；
- 步骤绑定锅具、灶位、烤箱等资源；
- 单厨房自动调度，再扩展多人 / 多厨房协同与移动交接。

### 5.5 完整四语言系统

V2 已有语言切换器、`profiles.locale` 和第一批 `zh-CN` / `zh-TW` / `en` / `de` 词条。V3 的任务不是“再做一次切换按钮”，而是把尚未覆盖的内容做完整：

- 全站按钮、表单、验证、错误、空状态、帮助、邮件和管理员文案进入 message catalog；
- 台湾厨房地区词汇、德语商品词、同义词和搜索别名映射到稳定 canonical id；
- 用户菜名、步骤、日志和导入原文永远保留，不因切换语言被批量改写；
- 完成 `zh-CN / zh-TW / en / de × 手机 / 平板 / 桌面` 布局矩阵、伪本地化、长德语换行和截图回归；
- 用简中、繁中、英文和德文分别跑登录、导入、编辑、采购、库存与公开菜谱主流程。

## 6. V4｜语音识别与多模态 AI 研究版

### 6.1 语音识别（ASR）学习与接入

- 系统学习 ASR 基础：波形/频谱、特征表示、CTC、Attention/Transformer、encoder-decoder、语言模型与解码；
- 先阅读并运行成熟开源模型（以 Whisper 类模型为 baseline），理解音频切分、时间戳、语言识别和解码过程；
- 对 B 站/小红书做饭视频建立 `audio → timestamp transcript` 流程，保留模型、版本、置信度和原始证据；
- 不要求从零训练大型 ASR；只有真实中文做饭语音、口音、背景音乐等错误足够稳定后，再评估 fine-tune / adapter / domain vocabulary；
- 研究推理性能、GPU/CPU 成本与本地/云端部署边界。

### 6.2 V2 视觉能力的高级研究延伸

YOLO baseline、冰箱/台面食材识别、小票区域定位已经前移到 V2。本节只保留更深入的训练、视频目标跟踪和与 ASR/OCR 的多模态研究，不再作为 V4 才开始识别的理由。

计划场景：

- 冰箱 / 冷冻柜照片中的食材候选：鸡蛋、牛奶、蔬菜、水果、饮料、包装肉类等；
- 厨房台面上的食材、调料瓶、锅具、刀具、砧板、量勺和容器；
- 德国超市货架或商品照片中的商品包装、价格标签和条码区域；
- 做饭视频中的锅、碗、食材包、调料容器和关键操作对象；
- 与 OCR 组合：YOLO / detector 先定位价格标签、包装文字或小票区域，再交给 OCR 读文字；
- 与线上冰箱组合：目标检测只生成“候选库存项”，必须经过 canonical ingredient 映射和用户确认后才能修改库存。

学习与实现顺序：

```text
预训练 YOLO baseline
  ↓
读取图片 / 视频并画 bbox
  ↓
理解 confidence、IoU、NMS、mAP
  ↓
收集自己的厨房 / 冰箱图像
  ↓
人工标注小规模数据集
  ↓
train / val / test 划分
  ↓
fine-tune
  ↓
错误分析
  ↓
导出 ONNX / 移动端或服务端部署评估
```

设计约束：

- 识别到“一个红色包装盒”不等于已经知道它是哪种 canonical 食材；视觉类别和食材词典必须分层。
- 对包装相似、遮挡严重、袋装散装等情况保留 `unknown` / candidate，不伪造确定结果。
- 自己的数据集需要记录图像来源、授权、标注版本和 train/val/test 划分，避免同一视频相邻帧泄漏到训练集和测试集。
- 如果现有预训练模型已经满足某一任务，不以“必须从零训练”作为目标；优先通过 fine-tune 学习完整工程流程。

### 6.3 多模态证据融合

CookingApp 中的“多模态”不是简单把很多数据一起丢给一个黑盒模型，而是把不同来源的证据对齐到同一时间轴/实体后再融合与交叉验证：

```text
音频 ASR：“加一点盐”
字幕：“加入盐”
视频帧 OCR：“盐 5 g”
YOLO / 视觉检测：出现盐罐 / 量勺
         ↓
时间轴对齐 + 实体归一化
         ↓
候选：盐 / 5 g
         ↓
证据一致性与冲突检测
         ↓
结构化菜谱候选 + evidence + confidence
```

- 研究语音、现成字幕、关键帧 OCR、YOLO/视觉对象、来源简介之间的一致性；
- 同一事实必须允许保存多个 evidence，不把 AI 输出覆盖原始证据；
- 当“语音模糊、画面明确”或多个来源冲突时，输出待核验而不是强行选一个答案；
- 可逐步比较规则融合、置信度加权、LLM/多模态模型融合等方案；
- 建立可复现实验集和指标，避免只看单个成功案例。

### 6.4 研究数据与训练边界

- CORD/公开数据用于学习通用 document parsing；德国小票使用独立真实测试集；
- YOLO / 目标检测优先使用公开预训练权重做 baseline，再建立小规模自有厨房/冰箱数据集；
- 视频研究集按“语音、字幕、OCR、视觉检测、最终人工确认菜谱”保存 ground truth；
- 公开数据集的已有标签不需要全部人工重标，但自己的训练/测试 ground truth 必须人工抽查和最终复核；
- 优先 fine-tune 或 adapter，不以“从零训练大模型”为目标；
- 所有训练数据明确版权、个人隐私与是否允许用于训练。

### 6.5 模块化重构与可选能力接口

模块化方案可行，但不采用“PWA 安装包里勾选若干组件”的桌面安装器思路。PWA 安装的是同一个轻量外壳；性能问题通过按路由下载代码、进入模块才加载数据、功能开关和稳定接口解决。这样用户仍只安装一次，未打开 OCR、财务或协作页面时，不必加载它们的重组件和业务数据。

V4 重构目标：

- 根层只保留 `SupabaseClient + AuthSession + ConnectionStatus + Locale`，不在 `CookingProvider` 启动时读取所有业务表；
- 将 `recipes / imports / pantry / shopping / finance / collaboration / receipt-ocr / inventory-vision` 拆成独立 domain module；
- 每个模块公开稳定的 `types + repository + service + route UI`，页面不能跨模块直连表；
- OCR、YOLO 或以后 ASR 只提交版本化 candidate/evidence；词典解析、人工确认和正式写库由主程序 service 编排；
- 使用动态 import、路由级 code splitting 和 feature flag；只有进入对应页面才加载重组件、模型桥接和数据查询；
- 用依赖方向和契约测试保证模块可替换，但不追求把所有模块发布成独立 npm 包或微服务；只有出现真实独立部署需求再拆；
- PWA 仍提供完整导航；管理员或实验功能可以 feature flag 隐藏。以后若做 Tauri/Capacitor 原生外壳，也复用同一模块接口，而不是复制业务逻辑；
- 设性能门槛：登录后首屏不等待 OCR/财务/协作数据；路由离开后取消无用请求；首屏 bundle、请求数和可交互时间进入回归指标。

选择性“安装模块”只有在未来出现离线模型包、桌面硬件驱动或企业部署时才有价值；那时可把大模型权重、相机/秤驱动做成可下载资源或原生插件，不把整个 CookingApp 拆成多个互不兼容的安装包。

### 7.1 Android / iOS 封装与上架预期任务

首选路线是先把响应式 Web/PWA 做稳定，再评估使用开源的 [Capacitor](https://capacitorjs.com/) 封装；它可以复用 HTML/CSS/JavaScript，但 App Store/Google Play 的签名、隐私、测试与审核仍需单独完成。封装不是“代码写完即可下载”。Windows `.exe` 只能安装在桌面电脑，不能作为手机安装包；[Android 可从官网分发签名 APK](https://developer.android.com/distribute/marketing-tools/alternative-distribution)，但仍有系统安装提示、开发者身份/签名要求；[欧盟 iPhone 的原生网页分发](https://developer.apple.com/support/web-distribution-eu/)仍需 Apple 授权、注册域名与 Notarization，不能等同于完全绕过审核。PWA 才是当前最轻、无需商店上架的手机入口。

#### 技术与账号材料

- 稳定的手机端生产站、PWA 图标与启动视觉、反向域名应用 ID（例如基于自有域名）、版本号与更新策略；
- Android Studio、Android 项目、AAB、upload key/keystore、Play App Signing、至少两类真机测试；
- iOS 的 macOS + Xcode 环境、Bundle ID、签名证书/Provisioning、Archive、TestFlight 和 App Store Connect；
- 相机/相册、通知、文件、剪贴板等原生权限只按实际功能申请，并在系统权限文案和隐私政策中逐项说明；
- Supabase OAuth/邮件回跳、深链接、Universal Links/App Links 和登录会话恢复需要按 App scheme 重新验收；
- Apple/Google 审核账号需要可用的测试登录，但不得提交真实用户密码或私人菜谱。

#### 商店与合规材料

- 应用名称、副标题/短描述、完整描述、关键词、分类、年龄分级、支持网址、联系邮箱；
- 正方形商店图标、启动图、手机截图；四语言上架时分别准备本地化描述与截图，截图使用虚构/演示账号数据；
- 隐私政策、服务条款、账号删除说明、用户反馈/举报入口；
- Apple App Privacy 与 Google Play Data safety：声明 Supabase、日志/监控、图片、账号邮箱及所有第三方 SDK 的收集、用途、共享和删除；
- 内容来源与商标说明：B站、小红书、下厨房标识只用于来源识别，不暗示官方合作；
- App Review/Play Console 审核说明、核心流程演示、需要登录时的审核账号和特殊操作说明。

#### 费用与时间预算（2026-08 查询基线）

| 项目 | 固定费用 | 现实时间预算 | 备注 |
|---|---:|---:|---|

### 7.2 中国大陆网站 / App 上线治理

- 当前 Sites + 境外服务用于德国/境外访问时，不把“迁入中国大陆节点”作为 V2 阻塞项；
- 如未来使用中国大陆服务器/CDN 向公众提供网站，应先准备大陆接入服务商、域名实名认证、主办者/负责人信息、网站名称与服务内容，办理非经营性 ICP 备案；备案本身官方不收费，材料齐全后的法定处理期限为 20 个工作日，但接入商初审和补件需额外缓冲；
- 备案通过后，网站主页底部显示备案号并链接工信部备案系统；域名、主体、接入或服务内容变化时维护变更；
- 如在中国大陆提供并分发原生 App/小程序/快应用，还要按届时规则办理 **APP 备案**，准备包名/应用 ID、签名证书指纹、公钥、平台和接入信息；已有网站备案不自动等于 App 已备案；
- 公开菜谱、评论/反馈、图片上传等用户内容扩大前，另做个人信息、内容审核、投诉举报、数据留存与跨境数据流评估；不能把 ICP 备案误解为全部合规已经完成；
- 官方依据：[非经营性互联网信息服务备案管理办法（2024 修订）](https://www.miit.gov.cn/gyhxxhb/jgsj/cyzcyfgs/bmgz/xxtxl/art/2024/art_84a0cfa0ebd049bbbe751dca9a008e56.html)、[备案办事指南与零收费](https://xzca.miit.gov.cn/bsfw/bszn/art/2017/art_4302aade098b4c4aa4966912d4308481.html)、[工信部 APP 备案通知](https://www.hunan.gov.cn/zqt/zcsd/202308/t20230809_29456035.html)。

## 9. 路线图维护规则

1. 新需求先写入本文件并标记版本与状态；没有版本的进入候选池。
2. 开始实施时同步到当前版本工作表，写负责人、前置条件和完成定义。
3. 用户反馈先进入 `99`，确认处理后再转成当前版本任务。
4. 发布后更新 CHANGELOG；版本结项后把经验沉淀到对应 `00` 类复盘。
5. 删除、替代和延期不能从历史中抹掉，必须保留原因和日期。
