# CookingApp V1 开发实施计划

## 1. 技术基线

- Next.js（App Router）+ TypeScript，手机优先响应式 Web/PWA。
- Tailwind CSS + 可访问性良好的组件库。
- Supabase PostgreSQL、Auth、Storage 与 Row Level Security。
- Vercel 预览/生产部署；自定义域名可在首版稳定后绑定。
- Vitest 负责单元/集成测试，Playwright 负责关键端到端流程。

## 3. 建议开发顺序

### M0：规格冻结

- 以 `database_schema.md` 为 migration 的唯一字段依据。
- 以 `feature_list.md` 的完成定义控制需求膨胀。
- 用 `ingredient_mapping.xlsx` 校验食材字段、枚举和首批样例。
- 从收藏夹抽取 10 个差异较大的视频：快手菜、烘焙、炸物、汤、替代食材明显的菜各若干。

### M1：工程骨架

- 初始化 Next.js、TypeScript、ESLint、Prettier、测试框架和 `.env.example`。
- 建立 public/auth/dashboard 路由分组以及统一错误、加载、空状态。
- 配置 GitHub Actions：类型检查、lint、单元测试、构建。
- 建立预览部署，不放真实密钥进仓库。

### M2：数据库与安全

- 按 0001–0008 顺序编写 migration 和种子。
- 先写 RLS 测试，再接页面；重点验证跨用户读取、匿名分享和私人日志。
- 生成 TypeScript 数据库类型，禁止页面直接散落原始 SQL。
- 建立 repository/service 分层，导入、分享和菜谱版本逻辑集中管理。

### M3：菜谱主流程

- 先实现手工新建菜谱，确保系统不依赖 B 站才能使用。
- 实现来源版、当前个人版和 snapshot 的保存逻辑。
- 完成标签组合筛选、全文搜索和“已有食材”筛选。
- 厨房模式只保存临时勾选状态，不意外改写菜谱。

### M4：B 站收藏夹导入

- 导出脚本只在用户本机读取登录态，输出标准 JSON；不记录 Cookie。
- 上传前显示条数、重复项和缺失字段；用户确认后再入库。
- 每项有 `pending/processed/duplicate/failed/skipped` 状态和错误原因。
- AI 仅生成候选数据；用量、温度和时长缺失时保留为空。

### M5：个人经验与德国食材

- 完成做菜日志、照片、评分、下次改进。
- 导入首批中英德食材名与德国超市货架/包装关键词。
- 替代品同时记录比例、适用场景、限制和验证状态。
- 对 gluten_status、过敏原和健康标签显示明确的确认来源。

### M6：分享、导出与生产

- 分享接口采用字段白名单，日志、owner_id、raw_metadata 永不进入匿名响应。
- 支持撤销分享和可选过期时间，二维码仅编码分享 URL。
- 提供 JSON/CSV 导出和恢复说明；验证 migration 能重建空库。
- 完成 SEO 基础、可访问性、错误监控与基本性能检查。

## 4. 测试矩阵

| 类型 | 必测场景 |
|---|---|
| 单元测试 | 食材/用量校验、标签过滤、版本号、导入数据规范化 |
| 数据库测试 | 唯一约束、删除来源后菜谱保留、RLS、公开字段白名单 |
| 集成测试 | 菜谱 CRUD、版本切换、日志、图片元数据、导入重试 |
| E2E | 登录→新建菜谱；导入→校对→个人版；分享→匿名查看 |
| 手机验收 | 首页、编辑器、厨房模式、照片上传、二维码分享 |

## 5. 风险与控制

| 风险 | 控制方式 |
|---|---|
| B 站页面/API 变化 | 导出器与导入器解耦；标准 JSON 作为稳定边界 |
| 197 条内容整理工作量大 | 先 10 条上线，再按 20–30 条批次处理 |
| AI 臆造配方 | 未知字段留空，所有候选有确认状态和人工编辑入口 |
| 公开分享泄露隐私 | RLS + 服务端字段白名单 + 自动化匿名测试 |
| 食材同义词造成重复 | canonical 名称、aliases、人工合并与唯一化规则 |
| 德国商品数据变化 | 外部引用保存 provider/id/同步时间，不硬编码为永久事实 |
| 功能膨胀 | 新需求先进入 V2 候选，不阻塞 V1 完成定义 |
