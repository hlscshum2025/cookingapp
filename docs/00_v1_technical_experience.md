更新日期：2026-08-18

## 1. V1 结论

CookingApp V1 已按 2026-08-12 调整后的范围结项，可以继续开发 V2。

V1 的核心交付不是“把所有设想一次做完”，而是建立一个可安全持续迭代的基础设施版：

- 邮箱注册、确认、登录、找回密码和登录后修改密码；
- Supabase 数据库、Auth、Storage 策略、RLS 与管理员/普通用户角色边界；
- B 站来源 JSON 导入、来源待办、手工核验、菜谱保存和做菜日志闭环；
- 菜谱 CRUD、标签筛选、厨房模式、个人经验记录与公开分享边界；
- DEV / PROD 环境分离、JSON/CSV 备份恢复、GitHub 与 Sites 发布链路；
- 手机主流程、异常重试、第二账号隔离和 10 条真实内容闭环验收。

德国实地采购、完整中英德词典、Storage 图片恢复、自定义 SMTP、错误监控等未被伪装成“已经完成”，而是经过范围调整进入 V2 或满足前置条件后再做。它们不再阻塞 V1 结项。

## 3. 最重要的架构经验

### 3.1 来源记录不能等同于菜谱

早期 JSON 导入会直接制造空菜谱，导致“视频收藏”和“已经整理好的菜谱”混在一起。最终稳定模型是：

```text
平台来源 → source_videos 待办 → 人工核验/录入 → recipe → cooking_logs
```

以后接入下厨房、小红书或其他平台时，Adapter 只能输出统一 `SourceDraft`，不能直接绕过人工核验写正式菜谱。

### 3.2 原始表达必须保留，不能强行换算

真实中式菜谱经常使用“少许、适量、一圈、两三根、一勺半”。正确数据设计是同时允许：

- `raw_amount`：保留原文；
- `amount_value`：只有可确定时才填数值；
- `unit`：克、毫升、勺、圈、个、片、段等；
- `verification_status`：区分已确认与待核验。

成本核算需要精确值，但不能为了核算而篡改来源证据。

### 3.3 私人原稿与公开内容必须分层

用户不能直接把私人 `recipes` 行切成 public。稳定流程是：

1. 用户提交公开申请；
2. 数据库生成字段白名单快照；
3. 管理员审核；
4. 审核通过后写入独立公开版本；
5. 私人日志、导入原始 metadata、邮箱和角色永不进入公开快照。

这样私人原稿后续修改不会绕过审核，也不会意外泄露做菜日志。

### 3.4 RLS 是最终边界，前端隐藏按钮不是权限

前端只能改善体验，不能阻止用户直接构造请求。安全验收必须覆盖：

- 匿名访问；
- 第二用户横向读写；
- 跨用户外键关联；
- `owner_id` 篡改；
- 普通用户自提权；
- 私有 Storage 路径；
- 业务 RPC 回归。

角色赋权必须由数据库管理端控制，`service_role` 和其他 Secret 不能进入浏览器、GitHub 或公开日志。

### 3.5 DEV / PROD 与备份恢复必须分开

开发环境和正式环境共用 Supabase 会把测试数据、迁移试验和误操作带进生产。V1 后期建立的正确做法是：

- localhost 只连接 DEV；
- Sites 正式站只连接 PROD；
- 恢复演练只在隔离 DEV 项目执行；
- 恢复时按依赖顺序处理主键、外键和关联表；
- JSON/CSV 业务备份与 Storage 图片分开管理。

### 3.6 登录、注册和密码恢复必须是三条流程

曾经把“首次设置”和找回密码混在一起，造成新用户误解。最终界面层级是：

```text
登录 → 注册新账号 → 重发注册确认邮件 → 忘记密码
```

Turnstile token 通常一次性使用，提交后刷新验证码是正常行为。Supabase 默认邮件服务只适合开发测试；面向普通用户开放时需要评估自定义 SMTP、发件域名信誉、限流和跨地区投递。

## 4. 导入与外部平台经验

- B 站导出器只在用户本机使用登录态，绝不上传 Cookie。
- 平台接口和页面结构会变化，导出器与 CookingApp 导入器必须通过稳定 JSON 边界解耦。
- 视频标题、简介和字幕只能作为证据，缺失的克数、温度和火候必须留空。
- 小红书与 B 站只能共享外层工作流，不能共用 BV 号或播放器解析逻辑。
- 对需要登录、验证码或存在反爬限制的平台，可靠兜底是“分享链接 + 分享文本 + 人工校对”，不把绕过限制作为产品能力。

## 5. GUI 与手机端经验

- 注册属于主要动作，找回密码属于低频辅助动作，视觉层级必须不同。
- 二级页面统一提供上下文返回，避免每个页面各写一套返回逻辑。
- 视频录入需要站内可暂停、音量和尺寸控制；打开原站应是显式按钮，不能让播放器任意点击跳走。
- 草稿按“账号 + 来源”隔离，正式云端保存成功后才清除。
- 标签筛选中心可以组合展示食材、作者、内容标签和工作流状态，但数据库语义必须分开。
- 手机端浮动组件必须避开底部导航，登录页不能出现采购车等业务悬浮控件。
- 页面内跳转、登录后预加载和非阻塞同步提示比整页刷新更适合移动端。

## 6. 工程与发布经验

- GitHub `main` 是正式源码基线；Sites 发布与 GitHub 合并需要分别验收。
- 临时分支合并后应及时删除，避免用户误以为代码未进入 `main`。
- Squash merge 会改变提交历史，分支显示 diverged 不等于功能未合入。
- 版本号、`package.json`、CHANGELOG 和部署版本必须在同一发布门禁中校对。
- 文档不能只勾选“写过代码”，还要区分：代码完成、已合并、已迁移、已部署、已实机验收。
- 当前 `CookingProvider` 和页面直连 Supabase 的耦合已经偏高；V2 应按功能触碰逐步迁移到 service/repository，而不是一次性重写。

## 7. V1 中被替代或延期的方案

| 原方案 | 最终处理 | 原因 |
|---|---|---|
| ChatGPT 登录 | 替换为邮箱 + 密码 | 公开访问不应要求 ChatGPT 账号。 |
| “首次设置 / 忘记密码” | 删除“首次设置”，拆分注册与找回密码 | 避免新用户误解入口。 |
| JSON 导入后自动创建空菜谱 | 取消，改为来源待办 | 收藏不等于完成菜谱。 |
| 用户直接公开私人菜谱 | 取消，改为审核快照 | 防止私人字段泄露和绕过复审。 |
| 德国词典与采购作为 V1 阻塞项 | 转入 V2 | 需要真实使用迭代，不应拖住基础设施结项。 |
| 自动字幕/OCR/AI 批处理 | 转入 V3/V4 | 图像自动化进入 V3；语音识别、多模态与目标检测研究进入 V4。 |
| 为验证继续重复录入更多视频 | 停止 | 10 条真实闭环和 P0-1～P0-5 已完成。 |

## 8. V2 开始前必须继承的约束

- 不覆盖正式库做恢复试验；
- 不把 Secret、Cookie、私人菜谱、日志或原始备份提交 GitHub；
- 不把未知用量自动伪造成克数；
- 不让平台 Adapter 直接写正式菜谱；
- 不用纯简繁转换替代地区词汇本地化；
- 不以“代码存在”代替两账号、手机端和生产环境验收。

### 9.3 V1 早期本地运行方式

当时的 Windows 本地启动方式为：

```powershell
git clone https://github.com/hlscshum2025/cookingapp.git
cd cookingapp
copy .env.example .env.local
npm install
npm run dev
```

这条基本命令仍然适用于 V2，但 V2 必须进一步区分 DEV / PROD Supabase 环境，并在发布前检查 `docs/03_dev_prod_database_sync.md`。

### 9.4 V1 早期登录与写入验收

V1 很早期曾使用 Supabase 邮箱魔法链接登录，并通过以下方式确认云端链路：

```text
.env.local Supabase 配置
        +
数据库 migration 已安装
        +
浏览器完成登录
        ↓
导入 / 编辑写入 Supabase
```

当时典型验收包括：

1. 在 `/login` 输入邮箱；
2. 通过邮件完成登录；
3. 在 Supabase `Authentication → Users` 确认用户；
4. 导入少量 B 站来源；
5. 验证云端而不是演示模式写入；
6. 重复导入验证 BV 去重；
7. 人工整理若干菜谱并新增做菜日志。

之后登录体系已改为“注册 / 邮箱确认 / 邮箱+密码登录 / 找回密码 / Turnstile”分离流程，因此魔法链接描述只保留用于说明项目演化历史。

### 9.5 V1 数据存放边界

| 内容 | 存放位置 |

### 9.6 V1 旧 README 边界的演化

旧 README 曾写过“V1 暂不含完整库存、购物清单、微信登录或多人协作”。其中：

- 基础采购车和线上冰箱已在 V2 提前实现；
- 成本、小票 OCR、繁中本地化进入 V2；
- 图像自动化与并行厨房进入 V3；
- ASR、YOLO 目标检测和多模态研究进入 V4；
- 微信登录、小程序和多人协作继续保留到更后版本按真实需求决定。

因此 V1 的边界只用于解释“为什么当时没有做”，不应继续限制当前版本。
