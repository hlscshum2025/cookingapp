# 成本、准备时间与多人厨房调度设计

更新日期：2026-08-04

## V2：每顿饭成本核算

成本不能只在菜谱里填一个总价，因为采购包装、实际用量、调料均摊和价格变化是四件不同的事。

### 建议数据

| 数据 | 示例 | 用途 |
|---|---|---|
| 采购记录 | 生抽 500 ml，€2.49，2026-09-01 | 保存真实购买价格与时间 |
| 包装净量 | 500 ml | 计算单位成本 |
| 本次用量 | 15 ml | 主食材和可量化调料按实际消耗计算 |
| 均摊方式 | 按用量 / 按预计次数 / 每餐固定估价 | 处理盐、香料、油等难以精确称量的项目 |
| 预计使用次数 | 50 次 | `购买价格 ÷ 预计次数` |
| 成本快照 | 本次菜谱食材合计 €4.83 | 历史价格变化后仍保留当时结果 |
| 损耗率 | 一把香菜可食用率 80% | 包装中不可食部分不应算作可用净量 |
| 共同采购分摊 | 一盒鸡蛋用于 3 道菜 | 同一批采购不能被重复计算整盒价格 |

推荐计算规则：

- 可称量食材：`本餐成本 = 购买价 × 本次用量 ÷ 包装净量`；
- 难称量调料：允许“估计使用次数”，`单次成本 = 购买价 ÷ 预计使用次数`；
- 极低价值调料：可设置每餐固定小额估价，但必须显示“估计”；
- 多人份：同时显示整道菜成本和每人份成本；
- 货币保存原币种，汇率换算只作显示，避免德国 EUR 与日本 JPY 历史数据被覆盖。
- 每次实际做饭保存“成本快照”，以后采购价变化也不会改写过去一餐的金额。

V2 首先做手工价格和用量；超市小票识别、实时商品价格和库存以后再接。

## V2：时间拆分

“总时间”不足以安排做饭，至少要分为：

- 亲手操作时间：切配、翻炒、包制等必须占用人的时间；
- 等待/烹煮时间：发酵、腌制、炖煮、烘烤等可并行时间；
- 提前准备量：例如提前 1 天腌制即 1440 分钟；
- 提前准备说明：冷藏、泡发、解冻、回温等条件；
- 每一步的持续时间和可否中断；
- 上桌截止时间：例如 18:30 必须完成。

当前编辑器已加入前四项，后续会把每一步扩展为可调度任务。

## V3：并行做菜规划属于什么算法

这个问题不是普通待办清单，而是组合优化中的调度问题：

- 菜谱步骤有先后关系，属于有向无环图（DAG）；
- 大火灶、小火灶、烤箱和案板都有容量限制；
- 一个步骤可能同时占用“厨师 + 灶位 + 锅”；
- 同一步可有不同执行模式，例如大火 8 分钟或小火 12 分钟；
- 多个厨房之间还有人员移动、食材转运和设备差异；
- 目标不只是最短总时间，还包括准时上桌、减少等待、菜品保温和公平分工。

最贴切的基础模型是：

1. **RCPSP（资源受限项目调度）**：处理步骤先后与有限灶位；
2. **MRCPSP（多模式 RCPSP）**：同一步可以选择不同火力、设备或厨房；
3. **多技能 RCPSP**：不同人会做的任务不同；
4. **Flexible Job Shop**：一个步骤可在多个可替代设备/厨房执行；
5. **多项目 RCPSP**：团圆饭的多道菜同时推进。

把你的例子翻成算法语言就是：每道菜是一组有先后关系的任务；“两个大火 + 两个小火”是两类容量分别为 2 的可再生资源；厨师、锅、案板、烤箱也各自是资源；提前一晚腌制是带最早开始时间/时间窗的前置任务；多个厨房则是可替代执行模式并附带移动和交接时间。

### 第一版求解器

建议使用开源 Google OR-Tools 的 CP-SAT：每个步骤建立开始、结束和持续时间变量；用 precedence 约束保证先后顺序，用 NoOverlap/Cumulative 限制灶位、锅和人员容量，再最小化最晚完成时间与误点惩罚。OR-Tools 官方把这类“任务顺序 + 有限机器”归为 Job Shop，并提供员工排班与 CP-SAT 示例：

- [OR-Tools Scheduling Overview](https://developers.google.com/optimization/scheduling)
- [The Job Shop Problem](https://developers.google.com/optimization/scheduling/job_shop)
- [Employee Scheduling](https://developers.google.com/optimization/scheduling/employee_scheduling)
- [CP-SAT Solver](https://developers.google.com/optimization/cp/cp_solver)
- [Multi-skill, multi-mode RCPSP 研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC10613272/)

### 分阶段实现

| 阶段 | 范围 | 算法 |
|---|---|---|
| V3.1 | 单人、单厨房、4 个灶位 | 规则排程 + CP-SAT 验证 |
| V3.2 | 多人、单厨房 | 多技能资源约束、任务分配 |
| V3.3 | 多厨房 | 多模式/多项目调度，加移动与交接时间 |
| V3.4 | 现场变化 | 滚动重排：某道菜延误后只重算剩余步骤 |

不要一开始训练 AI 模型。菜谱数量少、规则明确时，约束规划更可解释，也能明确告诉用户为什么某一步不能提前。以后有大量真实做菜日志后，再用机器学习修正“预计时长”，调度器仍负责满足硬约束。

求解目标建议采用分层权重：先保证食品安全、步骤先后和设备容量等硬约束；再最小化超出上桌时间、菜品完成后等待、人员冲突和总工期。这样不会为了“快两分钟”生成现实中无法执行的安排。
